## Ticket brief (course — commercial assistant)

You already have a working central API and a data pipeline feeding real-time dashboards. The company now needs something different: anyone on the **commercial team** should be able to ask a question in natural language and get a reliable answer, without manually digging through scattered documents.

The sales team keeps losing time answering questions from prospects and clients that are already answered somewhere in an internal document — policies, catalogs, procedures — but nobody can find them in time. The tech lead forwards a ticket with the commercial brief: they need an assistant that answers from a **salesperson's perspective**, with the voice and priorities of the business — **not** a search box that dumps raw database fragments.

### Core acceptance criterion (non-negotiable)

The **final answer must always be generated by a model from the retrieved context**. The raw result of the vector database search must **never** be returned directly to the client.

### Modularity criterion (non-negotiable)

Each responsibility must live in its own function so the technical team can swap any piece without touching the others:

| Responsibility | Function | Module |
| -------------- | -------- | ------ |
| Prepare / index data | `setup()` | `data/process/rag.py` |
| Store vectors (via embed + upsert inside setup) | `embed()` | `data/process/rag.py` |
| Search | `retrieve()` | `data/pipelines/rag.py` |
| Generate the answer | `query()` | `data/pipelines/rag.py` |

HTTP and UI are thin consumers of `query()` (and authenticated reindex calls `setup()` only).

---

## Function signatures (locked)

Match these signatures so modules and tests stay interchangeable:

```python
def setup() -> None: ...
def embed(text: str) -> list[float]: ...
def retrieve(query: str, *, k: int = 5, min_score: float) -> list[dict]: ...
def query(question: str) -> str: ...
```

- `retrieve` returns payload dicts plus internal `score` (L10) — never raw Qdrant SDK objects.
- `min_score` has no hard-coded default in the signature beyond env/config (`RAG_MIN_SCORE`, frozen `0.30` per L6); callers may pass it explicitly.
- `query` is the only function external consumers (API/UI) should call for answers.

## Goal

Deliver a modular RAG assistant for Brasaland commercial / operations users:

1. Natural-language questions over official internal docs in `docs/company-knowledge-base/`.
2. Answers from a **salesperson's perspective**, grounded only in retrieved context.
3. **Never** return raw Qdrant hits, chunk lists, or similarity scores as the API/UI answer — only the model-generated string from `query()`.
4. Four single-responsibility functions (`setup`, `embed`, `retrieve`, `query`) so indexing, embeddings, search, and generation can be swapped independently.

**Golden rules**

- RAG is a **knowledge-base consult**, not conversational memory (chat history is out of scope).
- Embedding model ≠ generation model (different model IDs / APIs).
- Prefer honest refusal over forcing weak retrieval into the prompt.
- Use **4Geeks-provided** student LLM access for embeddings + generation (no personal paid keys required for this milestone).
- Package installs: **`uv add` only** — never `pip` / `pipenv`.
- No LangChain, LlamaIndex, or other orchestration frameworks.

## CONTEXT — Brasaland (Milestone 7)

### 1. Introduction

At Brasaland, Operations and Marketing constantly get the same questions from location managers, customers, and new hires: how the points program works, waste protocols, allergens, supplier ordering. Today every manager answers “their own way,” which produces inconsistent answers between Colombia and Florida.

Felipe Guerrero (Operations Director) requested an assistant any location manager can use to answer **like a trained salesperson**: confidently, with correct data, without inventing information that isn’t in the official manuals.

**How this maps to the commercial ticket:** Felipe’s ops request and the commercial team brief are the same product need — stop hunting through manuals. The corpus is Operations/Marketing source docs; the **answer voice** is salesperson-facing. Location managers and commercial staff are both in-scope users of `POST /knowledge/query` and the backoffice UI.

The knowledge base must be built **only** from the source documents in §2. Do not invent additional content beyond those documents.

### 3. Domain Data Structure (Qdrant points)

Every point upserted into Qdrant must include, at minimum:

```json
{
  "id": "<uuid5 from L13>",
  "vector": [/* embedding */],
  "payload": {
    "company": "brasaland",
    "source_document": "loyalty-program | waste-protocol | menu-allergens | supplier-ordering",
    "section": "title or subtitle of the source section",
    "language": "en",
    "chunk_index": 0,
    "text": "chunk body used for prompt assembly"
  }
}
```

| Field | Allowed values / notes |
| ----- | ---------------------- |
| `id` | **Not** a random UUID each run. Deterministic UUID5 per **L13**: namespace + `f"{source_document}:{chunk_index}"` so upsert is idempotent (L2) |
| `company` | always `"brasaland"` |
| `source_document` | exactly one of: `loyalty-program`, `waste-protocol`, `menu-allergens`, `supplier-ordering` |
| `language` | `"en"` for this corpus (`.en.md` sources) |
| `text` | **Required** for prompt assembly. Course §3 lists metadata only; this milestone still requires `text` so generation uses retrieved chunk bodies and does not invent them |
| Collection name | `brasaland_knowledge` (L1) |

### 4. Answer KPIs and Thresholds

| KPI | Requirement |
| --- | ----------- |
| **Recall@3** | ≥ 80% of eval questions have the correct chunk in top-3 retrieved results |
| **Faithfulness** | Generated answer must not contain numeric data (%, amounts, kg) absent from retrieved chunks |
| **min_score** | Frozen at `0.30` (cosine) for current embed model — see L6. If nothing clears the threshold, say there isn’t enough information — never invent |

### 5. Seed Data Instructions

- Index all four complete source documents.
- Each document must produce **≥ 3 chunks** (not one chunk per document, not one chunk per line).
- Save `data/eval/test-queries.json` with **≥ 8** test questions covering all four documents (schema L11).

**Required eval seeds (from course deliverable examples) — include at least these:**

| Example question | Expected `source_document` |
| ---------------- | -------------------------- |
| How many points do I need for Gold tier? | `loyalty-program` |
| Does the BBQ Ribs dish have allergens? | `menu-allergens` |

Also include at least one allergen case that checks the model never answers **"zero risk"** (§6).

### 6. Business Constraints

- Answers stay in the project base language (`en` for these sources). If bilingual support is added later, the answer language must match the question.
- Never answer **"zero risk"** on allergen questions — follow `brasaland-menu-allergens.en.md` wording literally.
- Keep USD and COP amounts **exactly** as in source documents; no auto-conversion unless a later CONTEXT asks for it.
